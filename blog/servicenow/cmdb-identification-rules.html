CMDB Identification Rules: How to Think Through CI Matching

Reliable configuration data depends not only on discovering assets, but also on deciding whether incoming data represents an existing configuration item or a genuinely new one.

Technical learning guide · Concepts may vary by implementation

Identification and reconciliation solve different problems

Identification determines which configuration item an incoming observation belongs to. Reconciliation governs how incoming values are allowed to update attributes on that record. Keeping these responsibilities separate helps explain why a discovery run can complete yet still produce an unexpected CMDB outcome.

What makes a useful identifier?

A useful identifier distinguishes one CI from another consistently. Depending on the CI class and data source, identification can rely on a combination of attributes rather than a single value. The right choice depends on the stability, uniqueness, and availability of those attributes in the real environment.

Overly broad matching can merge distinct devices. Unstable matching values can cause duplicate records when a value changes or is missing. Review identifiers against real examples, including edge cases such as renamed hosts, rebuilt machines, virtual assets, and incomplete source data.

Why duplicate CIs may appear

  • Different sources report inconsistent identity attributes.
  • A required identifier is missing or changes over time.
  • Data arrives through paths with different class or mapping assumptions.
  • Existing records contain stale or conflicting values.
  • Matching logic does not reflect the asset lifecycle in the environment.

A safe investigation workflow

First, capture examples of the duplicate records and compare their identity attributes, class, source, and timestamps. Next, trace the incoming payload or discovery result to see which values were available when identification occurred. Then review the relevant identification and reconciliation configuration using current vendor documentation.

Test proposed changes with representative records in a non-production environment whenever possible. Do not alter identification logic broadly just to eliminate a single visible duplicate; the change may affect many records or cause unrelated CIs to merge.

Questions to ask before changing a rule

  • Which attributes are stable and unique for this CI class?
  • Do all authoritative sources populate those attributes?
  • What should happen when one attribute is absent?
  • Which source is permitted to update each field?
  • How will existing records and future updates be affected?
Practical reminder: Identification and reconciliation behavior is configuration- and release-dependent. Verify the actual rule order, class behavior, and data-source precedence in your instance before implementing changes.
