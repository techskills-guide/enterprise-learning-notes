ServiceNow Discovery Troubleshooting: A Practical Diagnostic Workflow

When a discovery run does not produce the expected configuration items, the fastest route to a useful answer is to isolate where the process stopped instead of changing multiple settings at once.

Technical learning guide · Review release-specific steps in official documentation

Start with the symptom, not a random setting

Discovery results are produced through a sequence of stages. Depending on the configured pattern and target, a run may involve scheduling, target selection, connectivity, credentials, classification, identification, and updates to the CMDB. A failure at one stage can look like a general discovery problem even when later stages are working correctly.

Record the target, run time, schedule, expected CI type, and actual result before troubleshooting. Compare one failing target with a similar target that succeeds; this can narrow the search without changing the environment.

1. Confirm the schedule and target scope

Check whether the schedule ran at the expected time and whether the target address or range is included. Review exclusions, filters, and any recent scope changes. If no relevant target was processed, credential or pattern changes will not solve the underlying issue.

2. Follow the execution evidence

Inspect the discovery status and related logs available in your instance. Find the first meaningful failure in the execution sequence rather than focusing only on the final summary. Note whether the run failed before connecting, during classification, while running a pattern, or when processing identification results.

3. Verify connectivity and credentials

For the relevant protocol and target, validate network reachability, required ports, credential selection, and the permissions of the account being used. A credential that works for one operating system or target type may not work for another. Follow your organization's secret-handling policy and never paste passwords or tokens into troubleshooting notes.

4. Check classification and pattern execution

If the target responds but the expected CI is absent or incomplete, determine whether classification occurred and whether the relevant pattern ran to completion. Review pattern output and error messages. Differences in operating-system versions, permissions, command output, or target configuration can affect results.

5. Investigate identification and CMDB updates

A successful connection does not guarantee that a new CI will be inserted. Identification logic may match an existing record, and reconciliation rules can affect which attributes are updated. Check for duplicate or unexpected CIs and inspect the identification outcome before trying to force a new record.

6. Make one controlled change at a time

Capture the original evidence, change one likely cause, and rerun a narrowly scoped test where safe. Compare the new execution with the original. Avoid broad scans or repeated production changes without approval; follow the organization's change-management and access policies.

A concise diagnostic checklist

  • Was the target included in the schedule?
  • Did the execution reach the target successfully?
  • Were the expected credentials selected and authorized?
  • Did classification and the relevant pattern complete?
  • Was the identification result consistent with the expected CI?
  • Did reconciliation or permissions affect the final record?
Release note: ServiceNow interfaces, log names, patterns, and available diagnostics can change between releases and configurations. Use the current official ServiceNow product documentation and your instance's evidence to confirm the exact steps.
